# Troubleshooting & Diagnostic Guide

Forensic diagnostic guide and solutions for common concurrency, persistence, and state synchronization pitfalls when using **`EricksonLopez.Concurrency`**.

---

## 1. Persistence & Dapper Issues

### Symptom: `ExecuteOptimisticAsync` Always Returns 0 Rows Affected (Permanent Conflict)
- **Root Cause 1**: The database version column name or data type does not match the SQL parameter `@ExpectedVersion`.
- **Root Cause 2**: The domain entity was initialized with version 0 while the database table contains a higher version number.
- **Diagnostic**: Inspect the SQL generated by `OptimisticUpdateBuilder` and verify database column types (`BIGINT` for `ConcurrencyVersion`).
- **Resolution**:
  ```csharp
  // Ensure the version parameter maps to a 64-bit integer
  var param = new { Id = entity.Id, ExpectedVersion = (long)expectedVersion.Version };
  ```

### Symptom: Multi-Tenant Query Desynchronization
- **Root Cause**: The `@TenantId` parameter was omitted or its value does not match the persisted record.
- **Resolution**: Always pass `tenantColumn` and `tenantParam` when invoking `OptimisticUpdateBuilder.BuildVersionedUpdate`:
  ```csharp
  string sql = OptimisticUpdateBuilder.BuildVersionedUpdate(
      tableName: "orders",
      setClauses: "status = @Status, total = @Total",
      idColumn: "id",
      versionColumn: "version",
      tenantColumn: "tenant_id",
      tenantParam: "TenantId");
  ```

## 2. In-Memory CAS & ConcurrencyController Issues

### Symptom: `InvalidOperationException`: "A reentrant Compare-And-Swap operation was detected for entity '...'"
- **Root Cause**: An asynchronous flow attempted to call `IConcurrencyController.ExecuteCasAsync` recursively or nested on the same `entityId`.
- **Diagnostic**: Inspect the call stack for nested `ExecuteCasAsync` invocations or delegates that trigger commands affecting the same entity.
- **Resolution**: Restructure the workflow so that each entity mutation occurs sequentially within distinct execution scopes. `IConcurrencyController` enforces strict non-reentrant mutual exclusion per entity ID to prevent self-deadlocks.

### Symptom: `TimeoutException`: "The in-memory concurrency lock for entity '...' could not be acquired within the configured timeout"
- **Root Cause 1**: Another thread is executing a long-running synchronous or blocking operation inside its mutation delegate.
- **Root Cause 2**: Cyclic lock ordering across multiple entities (Entity A requesting Entity B while Entity B requests Entity A).
- **Resolution**:
  1. Keep mutation delegates purely non-blocking and fast (avoid I/O or long calculations inside `mutate`).
  2. Increase `DefaultMaxAcquisitionTimeout` in `ConcurrencyOptions` if operations legitimately require more time:
     ```csharp
     services.AddEricksonLopezConcurrency(options =>
     {
         options.DefaultMaxAcquisitionTimeout = TimeSpan.FromSeconds(10);
         options.DefaultMaxExecutionTimeout = TimeSpan.FromSeconds(15);
     });
     ```

### Symptom: `InvalidOperationException`: "Entity of type '...' does not implement 'IMutableVersionedEntity' and the mutation delegate did not advance the entity version..."
- **Root Cause**: The entity is an immutable reference type (or record) and the mutation delegate returned an instance without advancing its version (`Version = currentVersion.Next().Value`).
- **Resolution**:
  - Implement `IMutableVersionedEntity` on the entity so `IConcurrencyController` can automatically advance the version:
    ```csharp
    public class Order : IMutableVersionedEntity
    {
        public string Id { get; init; } = string.Empty;
        public long Version { get; set; }
    }
    ```
  - Or, if using immutable records, advance the version explicitly using with-expressions:
    ```csharp
    await controller.ExecuteCasAsync(order, expected, order.Id, (current, ct) =>
    {
        return current with { Status = "Confirmed", Version = current.Version + 1 };
    });
    ```

## 3. Web APIs & ASP.NET Core Issues

### Symptom: Unexpected HTTP 412 Precondition Failed or 409 Conflict Responses
- **Root Cause**: The client sends the `If-Match` header with unnormalized quotes or an unrecognized ETag format.
- **Resolution**:
  ```csharp
  // Use the official extension helper to normalize quotes and discriminators:
  ConcurrencyToken? token = request.GetExpectedConcurrencyToken();
  ```

### Symptom: `ConcurrencyException` Not Handled by Middleware
- **Root Cause**: `app.UseConcurrencyConflictHandling()` was placed after endpoints in `Program.cs`.
- **Resolution**: Register the middleware before `app.MapControllers()` or `app.MapGroup()`.

## 4. Database-Specific Dialect Issues

### PostgreSQL: Recurring Serialization Failures (`40001`)
- **Root Cause**: Using `SERIALIZABLE` isolation level in transactions with high key contention.
- **Resolution**:
  1. Detect the failure using `PostgreSqlConcurrencyErrorClassifier.IsSerializationFailure(ex)`.
  2. Implement an exponential backoff retry policy with randomized jitter in the application or resilience layer (`EricksonLopez.Resilience`).
  3. Use explicit row locking: `WithLock(PostgreSqlLockMode.ForUpdate)`.

### SQL Server: Frequent Deadlocks (Error 1205)
- **Root Cause**: Concurrent queries read under default shared locks (`S`) and subsequently attempt escalation to exclusive update locks (`X`).
- **Resolution**:
  - Apply table locking hints to read with intent to update:
    ```csharp
    string query = "orders".WithSqlServerTableHint(SqlServerLockMode.UpdLockRowLock);
    ```

### SQLite: `database is locked` (`SQLITE_BUSY` 5)
- **Root Cause**: SQLite supports only a single concurrent writer. When another connection holds an active write lock, other write attempts fail immediately if no busy timeout is configured.
- **Resolution**:
  - Enable WAL mode (`PRAGMA journal_mode = WAL;`) and specify `Default Timeout = 30;` in the connection string.
  - Use `SqliteConcurrencyErrorClassifier.IsBusy(ex)` to classify transient lock contention and retry with jitter.
